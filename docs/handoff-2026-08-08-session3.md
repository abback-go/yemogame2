## 4. ⚠ 미해결 · 유저 판단 대기

### 4.1 유저 승인 필요

1. **창대 도약(vault) 폐지** — worker가 유저에게 묻지 않고 판단했다.
   근거: 창대쉬 체인 4.536u가 나브 위 창대 도약 3.902u를 앞질러 나브가 아무것도 게이팅하지 못하고,
   창대쉬가 상시 가능하므로 "창 없이는 못 나오는 포켓"이 원리적으로 성립하지 않는다.
   논리는 맞지만 **창대 도약은 원래 「창 꽂기」 시그니처의 일부였다.** 코드(`t:"vault"`/`REACH.vault`/`drawVault`)는 남아 있다.
2. **부유 대시 `dashFreezeY`** — 현재 `false`. 실측 `true` 4.18u / `false` 5.33u. 순수 감각 판단이라 안 건드렸다.
3. **창대쉬 충전 중 시각/충돌 괴리** — `charge` 3프레임에서 캐릭터가 작아지는데(응축 연출) 히트박스는 그대로. 0.2초.
4. **진동 세기** — 매우 약하게(0.7~1.0px) 잡아뒀다. 부족하면 `FX.shakeMaxFrac`만 올린다.

### 4.2 구조적 구멍 (다음 라운드)

**`GATE_MARGIN`이 `MEAS_EPS`를 참조하지 않는다.**

```
MEAS_EPS = ENV_STEP(0.1) + dashSpeed × CTRL.dt = 0.165u   ← 버킷 + 1스텝 이산화
GATE_MARGIN = max(0.30, ledgeSnap×3.5) = 0.300u
실효 여유 = 0.135u
```

허용치가 여유의 절반 이상을 먹는다. 지금은 안전하지만 **`dashSpeed`가 24u/s를 넘으면
허용치가 여유를 통째로 삼켜 게이트가 뚫리는데도 PASS**가 된다. 유도 단일진실원 원칙 위반이다.

### 4.3 설계 공백

**진짜 진행 게이팅(성물 = 능력 = 열쇠)이 이 맵에 하나도 없다.**
`gate:"sdash"`는 "해금형 능력 잠금"이 아니라 "이 테크 없이는 못 넘는 구간"이다.
수련장이라 당연하지만 **본편 설계에서 별도 축으로 다뤄야 한다.**

### 4.4 미실시

- **사람이 직접 조작한 손맛 검증** — 배포본으로 유저만 할 수 있다.
  판정할 것: 체공 0.2초가 답답한가 · 돌진 11u/s가 맞는가 · 2배 시야가 답답한가 · 달리기가 이제 발을 잡는가

## 4.5 기각 이력 — 다시 꺼내지 말 것

### 모바일(터치) 플레이 대응 — **기각** `[유저 확정 2026-08-08]`

유저가 *"20분 정도 걸리면 부가적으로 해볼까 했는데 비용이 너무 크네"*로 기각했다.

**측정 결과** (Playwright, 실제 폰 뷰포트):

| | 시야 | 캐릭터 점유 |
|---|---|---|
| 데스크톱 1920×1080 | 9.6 × 5.4u | 15.4% |
| **폰 가로 844×390** | **4.9 × 2.3u** | **36.6%** |
| 아이패드 가로 | 5.9 × 4.1u | 20.2% |

**기각 사유 2가지:**

1. **세로 시야가 설계 기준의 절반이다.** 맵은 최소 8.0 × 4.5u 전제로 설계됐는데
   폰 가로는 2.3u다. **이단강림 2.886u > 화면 세로**, 4단 체인 4.536u = 화면의 2배.
   ⇒ 데스크톱에서 규칙까지 만들어 없앤 **맹목 점프가 폰에서는 기본값**이 된다.
   (배율 1로 내리면 8.4 × 3.9u — 가로는 해결, 세로는 여전히 3.9 < 4.5)
2. **창대쉬 8방향 입력이 버튼으로 안 된다.** 이식이 아니라 **UX 설계**라 왕복이 필요하다.

**되살릴 때 참고** — 터치 처리·뷰포트 메타는 현재 **0개**다(순수 키보드).
만든다면 창대쉬는 **「오른쪽 화면 드래그 → 조준 → 떼면 발사」**가 유력하다.
창대쉬가 *"누르면 0.2초 체공 후 방향 확정"* 구조라 드래그 조준과 궁합이 좋고,
키보드보다 오히려 직관적일 수 있다. 맵 재설계는 **금지**(19항목 검증이 깨진다).
