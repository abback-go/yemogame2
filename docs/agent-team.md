> 근거 이론 = `docs/game-design-theory.md`(모그 강의 학습 정본).

## ★ 새 세션이 먼저 할 일 — 이 절만 지켜도 방식이 유지된다

### 1) 확인 (30초)

```bash

```

없으면 **git 이력에서 복원**하고 유저에게 알린다. 있으면 그대로 쓴다 — **다시 설계하지 마라.**

### 2) 작업이 들어오면 이 흐름을 탄다

```
유저 요청
   │
   ├─ 기획 판단 · 컨셉 · 통합 · 대화 ──────────────▶ advisor 직접 (위임 금지)
   │
   ├─ 시스템 설계 ──▶ system-designer ──┐
   ├─ 수식 · 수치 ──▶ balance-designer ─┤
   ├─ 데이터 채우기 ▶ content-writer ───┼──▶ design-critic 판정
   │                  (시스템 있어야)    │      │
   └─ 조사 ─────────▶ researcher ───────┘   ┌──┴──┬────────┐
                          │              APPROVE REVISE  REJECT
                          │                 │      │        │
                          └──────────┬──────┘   재제출   다시 설계
                                     ▼
                        ★ advisor 재검증 (원문 대조 · 수치는 직접 실행)

                                  advisor 커밋
```

### 3) ★ 자주 하는 실수 — 이걸 하면 방식이 무너진다

| ❌ 하지 말 것 | 왜 |
|---|---|
| **혼자 다 하기** | 반론자 없이 쓰면 08-09에 세 번 난 사고(전제 충돌·폐기된 근거·층위 누락)가 반복된다 |
| **`design-critic`을 건너뛰고 유저에게 올리기** | 반려권이 무의미해진다. **반려당한 초안을 advisor가 임의 통과시킬 수 없다** |

| **기획 의도를 슬쩍 바꾸기** | 오너의 영역이다. 문제가 보이면 **바꾸지 말고 쟁점으로 보고** |

| **"해봐야 알죠"로 끝내기** | 이론 §1.4 — 그 뒤로 아무도 그 말을 신뢰하지 않는다 |

## 0. ★ 강의의 5직무와 우리 팀의 대응 `[유저 지적으로 재정리 2026-08-09]`

강의(이론 §4.2)는 기획을 **컨셉 / 시스템 / 콘텐츠 / 밸런스 / 유료화**로 나눈다. 우리 팀과 대조하면:

| 강의 직무 | 우리 | 판단 근거 |
|---|---|---|
| **시스템 기획** | ✅ `system-designer` | 그대로 |
| **콘텐츠 기획** | ✅ `content-writer` | 그대로 |
| **밸런스 기획** | ✅ `balance-designer` | **초기 구성에서 누락됐던 것을 유저 지적으로 추가.** 기획서에 **데미지 공식이 없고**(이론 §7의 대표 예시), §11-2 약점 배율이 *"최우선 튜닝"*으로 남아 있으며, 이론 §8.3이 **매직 넘버 탐색 계획 부재**를 경고한다 |
| **컨셉 기획** | ❌ 두지 않음 — **오너 + advisor의 영역** | 팀 규칙 §4에서 **기획 의도 변경권을 오너에게만** 두기로 했다. 컨셉 에이전트를 두면 그 권한과 정면 충돌한다. 컨셉을 *정리·문서화하는 노동*은 advisor가 직접 한다(`CLAUDE.md` 작업 프로토콜) |
| **유료화 기획** | ❌ 현 단계 불필요 | 스팀 **단품 판매**이고 DLC·과금 설계가 없다. 출시 후 필요해지면 신설 |

**강의에 없는데 우리가 추가한 둘** — `design-critic` · `researcher`:

> 강의는 **회사 조직을 전제**한다. 회사에는 이미 팀장·동료 기획자·리뷰 프로세스가 있어서 초안이 여러 눈을 거친다.
> **우리는 1인 + AI라 그 리뷰 기능이 통째로 없다.** `design-critic`이 그 빈자리다.
> `researcher`는 강의 8강의 **역기획서(남의 게임을 분석해 배우는 것)** 를 노동으로 분리한 것이다.

## 1. 왜 이 구성인가

직무 분류를 그대로 복사하지 않고 **실제 병목**에서 출발했다 — `2026-08-09` 하루의 실측:

| 관찰 | 도출 |
|---|---|
| advisor가 논리 구멍을 **3번 놓쳤고 전부 유저가 잡았다**(전제 충돌 · 폐기된 규칙에 기댄 근거 · 층위 누락) | **부족한 건 손이 아니라 반론자다** ⇒ `design-critic` 신설 · **반려권** |
| worker 조사 2건(아르피아·표절)은 잘 돌아갔다 — 특히 **한계를 정직하게 보고**해서 신뢰도 판단이 가능했다 | `researcher` 유지 · **정직 고지를 규칙으로 승격** |
| 문서가 전부 컨셉 레벨이라 **구현이 불가능하다**(이론 §8.2 진단) | `system-designer` 신설 — 7단계 산출물 |
| 시스템이 없어 콘텐츠를 채울 수 없다 | `content-writer` — **시스템 기획서가 없으면 작업 거부** |

## 2. 역할

| 에이전트 | 하는 일 | 도구 | 합격 기준 |
|---|---|---|---|
| **system-designer** | 컨셉 → **알고리즘 + 데이터**. 기획서 7단계 | 읽기·쓰기 | **읽고 그대로 구현 가능한가** |
| ★ **design-critic** | 플레이어처럼 이익을 최대화해 깨본다 · 해석의 여지 · 전제 충돌 | **읽기 전용** | 오늘 유저가 잡은 세 건 같은 걸 잡는가 |
| **balance-designer** | **수식과 수치.** 데미지 공식 · 성장 곡선 · 약점 배율 · 자원 수급 | 읽기·쓰기 + `Bash` | **검산을 실제로 돌렸는가 · 역검증했는가** |
| **researcher** | 웹 조사 · 레퍼런스 · 표절 검증 | 읽기 + 웹 | **한계를 정직하게 고지하는가** |
| **content-writer** | 시스템 위에 데이터를 채운다 | 읽기·쓰기 | 시스템 규칙을 벗어나지 않는가 · 심부름이 아닌가 |

> ★ **밸런스와 손맛은 다르다.** 게임필(입력 버퍼·코요테 타임·히트스톱·진동)은 **오너만** 정한다(§6.9 — AI가 대신 못 하는 유일한 영역).
> 밸런스(공식·곡선·수급)는 **수식과 시뮬레이션의 문제라 설계 가능**하다. `balance-designer`는 손맛을 침범하지 않되,
> **인스펙터에 노출할 파라미터와 후보 범위**까지 만들어 오너에게 넘긴다 — *"해봐야 안다"*로 끝내지 않는다(§6 공통 규칙).

> **`design-critic`이 읽기 전용인 것은 의도된 설계다.** 비판자가 직접 고치면 비판이 아니게 되고, 자기가 고친 것을 다시 비판할 수 없다.

## 3. ★ 반려권의 작동 `[유저 승인]`

```
system-designer 초안 ──▶ design-critic 판정
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
          APPROVE          REVISE          REJECT
              │               │               │
              ▼               ▼               ▼
        advisor 재검증    지적 고쳐 재제출   다시 설계
              │
              ▼
         오너(유저) 최종 승인
```

- **REJECT 사유는 셋뿐이다**(그 외는 REVISE): ①게임을 망가뜨리는 이익 최대화 경로 ②확정 전제와 충돌 ③핵심 규칙에 해석의 여지가 있어 구현 불가.
- **반려당한 초안은 오너에게 올라가지 않는다.** advisor가 임의로 통과시킬 수 없다.
- ⚠ **무한 루프 방지 — 3회 규칙**: 같은 사안이 **3회 반려되면 중단**하고, advisor가 **쟁점을 정리해 오너에게 올린다.** 판정은 유저가 한다.
- **`design-critic`이 건드리지 않는 것**: 기획 의도 자체 · 유저 씨앗 대기 중인 `[미정]` · 취향(재미의 판단은 오너 몫).

## 4. 권한 — 기획 의도는 누구도 못 바꾼다

> **이론 §1.6**: *제대로 된 기획자는 기획 의도를 중간에 바꾸지 않는다. 의도는 살린 채 구현 방법을 절충한다.*

| | 기획 의도 | 구현 방법 | 데이터 값 |
|---|---|---|---|
| **오너(유저)** | ✅ 유일한 변경권 | ✅ | ✅ |
| **advisor** | ❌ — 쟁점으로 올린다 | ✅ 제안 | ✅ |
| **에이전트** | ❌ | ✅ 제안 | ✅ |

- 에이전트가 *"의도 자체가 문제"*라고 판단하면 **바꾸지 말고 「쟁점」으로 보고**한다.
- **선례**(2026-08-09): 유저의 「신들이 몸에 깃든다」가 증인 구조를 깨뜨렸을 때 — 의도를 되돌리지 않고 **「눈을 뜨는 건 하나뿐」으로 절충**했다. 이것이 이 팀이 따를 표준 동작이다.

## 5. advisor(메인 세션)의 자리

> **이론 §1.3**: *같이 일하는 사람 중에 나보다 더 고민을 많이 한 사람이 단 한 명도 없어야 한다.*

이 문장은 위임할 수 없다. advisor는 **기획 의도의 수호자이자 통합자**로 남는다.

- **위임한 결과는 전부 재검증한다** — 에이전트 보고를 그대로 믿고 커밋하지 않는다(기존 `CLAUDE.md` 원칙).
- **오너와의 대화·최종 보고**는 advisor가 한다.
- **에이전트 산출물의 커밋 책임**도 advisor에게 있다.

## 6. 공통 규칙

1. **한국어.** 코드 식별자·경로·라이브러리명만 원문.
2. **`[미정]`에는 반드시 「누가·언제·무엇을 기준으로」를 함께 적는다.** 그냥 `[미정]`은 해석의 여지다.
3. **`docs/unity/tuning.json`의 `PHYS`는 불가침.** 맵 게이팅 전체가 걸려 있다.
4. **`archive/story-track.md` §3(취향·기각 이력)에서 기각된 방향을 다시 제안하지 않는다.**
5. **비용을 계상한다** — 신규 방·NPC·시스템은 개수를 세어 보고한다(1인 2년 스코프).
6. **"해봐야 알죠" 금지.** 손맛 판정이 필요한 항목도 **무엇을·어떤 후보 범위에서** 판정할지까지는 설계해 둔다.

## 7. 첫 운영 기록 `[2026-08-09]` — 「첫 시스템 기획 대상 선정」

유저 지시(*"그것 또한 너희끼리 팀으로 대화하며 정해봐"*)로 팀이 3라운드 논의했다.
**제안**(system-designer) + **병목 보고**(content-writer) → **검토**(design-critic) → **합의**(system-designer).

### 결과

- **첫 대상 = 「월드 그래프 · 게이팅 · 복귀」** — 방·연결·게이트 스키마 + **게이트 조건식 3축**(도달 kit · 진행 상태 · 발현 계열) + 사당·복귀·이동 자원 불변식.
- **판정 = REVISE**(9건 지적). designer가 **6건 수용 · 3건 반박**.
- **순서**: ①월드 그래프 → ②습득·성장 → ③지도·정보(§11-11 판정 후) → ④가호(손맛 3건 판정 후) → ⑤퀘스트·대화·보상. `balance-designer`는 ②④와 병행.

### ★ 이 논의가 실제로 잡아낸 것 — **팀이 작동한다는 증거**

| 발견 | 내용 | advisor 재검증 |
|---|---|---|
| **기획서 버그 1** | §6.1(이동기 자체 마나·쿨) ↔ §6.3(기본 층 마나 0) **정면 충돌** ⇒ 마나가 붙으면 **영구 소프트락** 성립 | ✅ 원문 대조 확인 → **§11-12 신설** |
| **기획서 버그 2** | 적 무스케일링 + 가호 순차 획득 ⇒ **최후반 몰아치기가 항상 최적** ⇒ §9.3-③ 레이어링(가장 싼 스코프 방어축) 사장 | ✅ 논리 확인 → **§11-13 신설** |
| **비용 은폐 적발** | designer가 C-1을 *"덤으로 함께 닫힌다"*고 계상 → critic이 **비용 미계상**으로 지적 → designer가 **실측**해 자기 주장 철회 | ✅ **재현 완료** — `GATE_MARGIN` 0.30→0.465 시 razor 5→16, **19/19 → 18/19 FAIL**(10쌍 신규 위반). 원복 후 19/19 정상 |
| **자기 오류 인정** | designer의 *"유저 지시와의 충돌은 겉보기"* → critic이 `TODO.md:87` 원문(**「지형 문법」이 유저가 미룬 묶음 안에 있다**)을 들이댐 → designer 철회 | ✅ 원문 확인 |
| **정당한 반박** | critic이 §7.2 *"얼려 만드는 발판"*을 하드 게이트라 판정 → designer가 **그 문장은 신전 챌린지 룸 서술이지 월드 지형이 아님**을 원문으로 반박, 승격도 연기도 아닌 **경계 규칙**으로 해소 | ✅ §7.2 원문 확인 — 반박이 옳다 |

> **읽을 것**: 비판자가 반려권을 쥐자 **양쪽 다 원문을 열어 대조하기 시작**했다. 이 프로젝트에서 반복된 사고(폐기·미확인 근거에 기댄 판단)를 막는 구조가 실제로 작동했다.
> 그리고 **비판자의 지적이 전부 옳지는 않았다** — 3건이 반박됐고 그 반박도 근거가 있었다. 반려권은 거부권이 아니라 **근거를 강제하는 장치**다.
