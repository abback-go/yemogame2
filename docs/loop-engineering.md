# 루프 엔지니어링 — 자율 반복 시스템 설계

> **정의** `[유저 2026-08-09]`
> *"사람이 매번 대화창에 명령을 입력하는 대신, AI 에이전트가 **목표와 종료 조건**을 달성할 때까지
> 스스로 **판단·실행·검증·수정**을 반복하는 **자율 시스템을 설계**하는 방식."*
>
> **지위**: 이 프로젝트의 **작업 실행 방식 정본.** 팀 구성(`agent-team.md`)이 *누가* 하는가라면, 이 문서는 *어떻게 굴리는가*다.
> **유저 요구 3조** — ①루프 엔지니어링 방법을 알 것 ②**토큰을 100% 채우지 말 것** ③**루프의 끝(goal)을 신경 쓸 것.**

---

## 1. 루프의 해부 — 다섯 부품

자율 루프는 아래 다섯이 **전부** 있어야 성립한다. 하나라도 빠지면 루프가 아니라 그냥 반복문이다.

| # | 부품 | 없으면 생기는 일 |
|---|---|---|
| 1 | **GOAL — 무엇이 완성인가** | 영원히 돈다. 또는 목표가 표류한다 |
| 2 | **PROGRESS — 한 바퀴가 무엇을 전진시키는가** | 제자리를 맴돈다(같은 것을 계속 다시 씀) |
| 3 | **CHECK — 달성 여부를 누가 어떻게 판정하는가** | 자기가 다 됐다고 선언한다 |
| 4 | **EXIT — 언제 멈추는가**(성공/실패/교착/예산) | 예산을 태우거나 무한히 돈다 |
| 5 | **HANDOFF — 멈췄을 때 무엇을 남기는가** | 다음 세션이 처음부터 다시 한다 |

### ★ 1.1 GOAL 작성 규칙 — 유저 요구 ③

> **나쁜 goal**: *"GDD를 잘 만든다"* · *"기획을 구체화한다"* · *"충분히 자세해질 때까지"*
> **좋은 goal**: **세어서 판정할 수 있는 것.**

좋은 goal의 세 조건:

1. **관찰 가능** — 달성 여부를 사람 판단 없이 기계적으로 셀 수 있다. *"지역 7곳 × 7항목이 채워졌고 각 지역이 APPROVE를 받았다"*는 셀 수 있다.
2. **단조 진행** — 매 바퀴가 goal에 **가까워지기만** 한다. 되돌아가는 루프는 종료를 보장할 수 없다.
3. **상한 존재** — 최대 몇 바퀴인지 미리 안다. *"다 될 때까지"*는 상한이 아니다.

### ★★ 1.1-a 범위는 오너가 정한다 — **예시를 목록으로 굳히지 마라** `[2026-08-09 실제 사고]`

> goal의 세 조건은 **범위가 확정된 뒤에야** 판정할 수 있다. 그런데 그 범위를 **advisor가 임의로 채우는 사고**가 실제로 났다.
> 유저가 *"어떤 맵들이 있고, 어떤 퀘스트가 있고, 인물은 어떻고 **등등**"* 이라고 **예시**를 들었는데,
> advisor가 그것을 **「지역 7곳 × 항목 7개」라는 확정 GOAL**로 박았다. 유저 정정: *"그게 다가 아니야."*

- **판별법**: 오너의 발언에 *"등등" · "예를 들면" · "같은 것"* 이 있거나, 목록이 **열린 채로 끝나면** 그것은 예시다.
- **처리**: 예시는 `[예시 · 전체 아님]`으로 적고 **오너 확정을 받은 뒤에** goal에 넣는다.
- **왜 치명적인가**: 잘못된 범위로 시작한 루프는 **끝까지 잘못된 것을 만든다.** 그리고 자율 루프라서 **아무도 중간에 안 묻는다.**
  같은 날 「챌린지 룸」(advisor 발명이 정본에 확정처럼 앉아 있던 건)과 **같은 유형의 사고**다.

⚠ **가장 흔한 실패는 「완성도」를 goal로 잡는 것**이다. 완성도는 올릴수록 더 올릴 게 보이므로 **수렴하지 않는다.**
대신 **범위(무엇을 다루는가)를 goal로 잡고 완성도는 품질 게이트로 처리**한다 — 「지역 7곳」은 끝나지만 「충분히 자세히」는 안 끝난다.

### 1.2 EXIT — 네 가지 종료

| 종료 | 조건 | 남기는 것 |
|---|---|---|
| **성공** | GOAL 달성 | 산출물 + 유저 승인 요청 |
| **예산** | 토큰 잔여가 임계 미만(§3) | **완성분까지 커밋** + 다음 시작점 |
| **교착** | 같은 항목 3회 반려(팀 규칙 §3) | **쟁점을 오너에게** — 판정 없이는 진행 불가 |
| **안전** | 최대 바퀴 수 초과 | 무엇이 안 끝났는지 + 왜 |

**교착 종료가 가장 중요하다.** 자율 루프의 진짜 위험은 실패가 아니라 **틀린 방향으로 끝까지 가는 것**이다.
그래서 이 프로젝트의 루프는 **판단이 갈리면 멈추고 오너에게 묻는다**(`agent-team.md` §4 — 기획 의도는 오너만).

## 2. 우리 루프 — GDD 지역 루프 ⏸ **보류 중** `[유저 지시 2026-08-09]`

> ## ⏸ **이 루프는 아직 시작할 수 없다 — 범위가 미확정이다.**
> 유저 지시: *"루프는 우선 잠깐 보류하자. 기억만 해두고 나머진 나중에 마저 설정할게."*
>
> ⚠ **advisor 오류 기록**: 유저가 GDD 항목과 지역을 말할 때 그것은 **예시**였는데,
> advisor가 **확정 목록으로 굳혀 GOAL에 박았다.** 유저 정정 —
> *"지역 7곳은 몇몇 예시를 들어준거지, 그게 다가 아니야. 항목도 예시를 들어준거지, 그것만 하면 되는건 아니야."*
> ⇒ 아래 목록은 전부 **`[예시 · 전체 아님 · 오너 확정 대기]`**.

### 2.1 GOAL — **범위 확정 후 완성된다**

```
GDD-GOAL (틀만 확정 · 값은 대기):
  대상 지역 각각에 대해 정해진 항목이 채워지고 design-critic APPROVE를 받는다.
  달성 판정: 완성 지역 수 == 전체 지역 수

  지역 목록  [예시 · 오너 확정 대기]: 序신전 · 늑대의 땅 · 여우의 땅 · 기계도시 · 용의 땅 · 인간 마을 · 신계 …
  항목 목록  [예시 · 오너 확정 대기]: 컨셉·룩 / 공간 구조 / 인물 / 퀘스트 / 스킬 습득 / 길을 여는 방식 / 진입·퇴장 …
```

**착수 조건**: 위 두 목록을 오너가 확정한다. **그 전에는 이 루프를 시작하지 않는다** —
범위가 미정인 채로 돌면 goal이 "셀 수 있는 것"이 아니게 되어 §1.1 조건 1·3이 무너진다.

### 2.2 2단 구조 — 왜 지역별로 바로 못 가는가

지역끼리 얽혀 있다(늑대 땅에서 얻은 능력이 여우 땅을 연다). 각자 쓰면 앞뒤가 어긋난다.

```
루프 0 (1회) — 전역 배분표
   어느 지역에서 무엇을 배우고 / 그것이 어디를 여는가 / 무엇을 들고 나오는가
   ⇒ 이 표가 각 지역 루프의 입력이자 제약이 된다

루프 1~7 (반복) — 지역 하나씩
   작성(system-designer + content-writer) → 검토(design-critic) → 수정 → 재검토
   APPROVE면 다음 지역, REVISE면 같은 지역 재시도(최대 3회)
```

### 2.3 한 바퀴의 내부

```
  ┌──────────────────────────────────────────────┐
  │ ① 입력: 전역 배분표 + 앞선 지역들의 확정분     │
  │ ② 작성: 7항목을 채운다                        │
  │ ③ 검토: design-critic — 세 검사 + 앞 지역과의 정합 │
  │ ④ 판정: APPROVE / REVISE / REJECT             │
  │ ⑤ REVISE·REJECT면 ②로 (같은 지역 최대 3회)     │
  │ ⑥ APPROVE면 커밋 + 유저 보고 → 다음 지역       │
  └──────────────────────────────────────────────┘
```

**PROGRESS**: 한 바퀴 = 지역 하나 완성. 완성분은 되돌리지 않는다(단조).
**CHECK**: `design-critic`(반려권 보유 · 읽기 전용). advisor가 그 위에서 재검증.
**HANDOFF**: 지역마다 파일이 남고, 다음 시작점이 TODO에 기록된다.

### 2.4 ★ 자율성의 경계 — 어디까지 혼자 하는가

| | 루프가 스스로 | 오너에게 묻는다 |
|---|---|---|
| **작성·검토·수정** | ✅ 전부 자율 | |
| **품질 판정** | ✅ `design-critic` | |
| **기획 의도 변경** | ❌ | ✅ **항상** |
| **확정 전제와 충돌** | ❌ | ✅ 즉시 중단 |
| **3회 반려된 쟁점** | ❌ | ✅ 정리해서 올림 |
| **커밋** | ✅ (미승인 표시 달고) | 최종 승인은 오너 |

⇒ **루프는 문서를 만들지만 확정하지는 않는다.** 유저는 매 지역 보고를 받고, 마음에 안 들면 그 지역만 다시 돌린다.

## 3. ★ 토큰 예산 — 유저 요구 ②

> **100%를 채우지 않는다. 마무리에 쓸 몫을 반드시 남긴다.**

한도까지 태우면 **결과를 정리·검증·커밋할 여유가 없어져** 작업이 통째로 날아간다. 그래서:

| 구간 | 비율 | 용도 |
|---|---|---|
| **작업** | **~70%** | 루프 본체(작성·검토·수정) |
| **마무리** | ~20% | advisor 재검증 · 커밋 · 유저 보고 |
| **여유** | ~10% | 예상 못 한 재시도 |

**멈추는 규칙**: 다음 바퀴의 예상 비용이 남은 작업 예산보다 크면 **그 바퀴를 시작하지 않는다.**
시작한 뒤 중간에 끊기는 것이 가장 나쁘다 — 절반짜리 산출물은 다음 세션이 신뢰할 수 없다.

```js
// Workflow 스크립트에서
const RESERVE = 0.30;                        // 마무리+여유 몫
const COST_PER_REGION = 120_000;             // 실측 후 갱신
while (regions.length && budget.total &&
       budget.remaining() > budget.total * RESERVE + COST_PER_REGION) {
  ...
}
```

⚠ **`budget.total`은 유저가 예산을 지정했을 때만 채워진다.** 지정이 없으면 `null`이고 위 식이 무력해진다.
⇒ **긴 루프를 돌릴 때는 예산을 명시해 주십시오**(예: 프롬프트에 `+300k`). 없으면 **바퀴 수 상한**으로만 제어한다(기본: 한 세션 3지역).

**실측 기준선** `[2026-08-09]`: 시스템 기획서 1편(설계→검토→수정→재판정 4에이전트) = **약 817k 토큰 · 70분.**
지역 GDD 1편은 그보다 가벼울 것으로 보나(스키마·알고리즘이 없다) **첫 지역을 실측한 뒤 위 상수를 갱신한다.**

## 4. 무한 루프를 막는 장치 셋

1. **바퀴마다 진행이 있어야 한다** — 같은 지역을 재시도할 때 **지적이 줄지 않으면** 그것은 진행이 아니다. 3회 규칙이 잡는다.
2. **재탕 금지** — 검토자는 **이미 다룬 지적을 반복하지 않는다**(`design-critic` 정의). 새 지적만 센다.
3. **상한 이중화** — 지역별 3회 × 전체 지역 7 = 최대 21바퀴가 이론상 상한이고, 실제로는 예산이 먼저 걸린다.

## 5. 이 프로젝트에서 이미 검증된 것

`agent-team.md` §7의 첫 운영 기록이 **루프 한 바퀴의 실증**이다.

- 검토자가 **12건 지적 → 설계자가 전부 반영 → 재검토에서 재탕 0건**. **PROGRESS가 실제로 발생**했다.
- 설계자의 **반박 1건이 검토자에게 수용**됐다 — 반려권이 거부권이 아니라 **근거를 강제하는 장치**로 작동.
- 그리고 2차에서 **7건이 새로 나왔다.** 여기서 얻은 교훈: **품질을 goal로 잡으면 안 끝난다.** 파고들수록 새 지적이 나온다.
  ⇒ 그래서 GDD 루프의 goal은 **「범위 7×7」이지 「완성도」가 아니다.**

## 6. 새 세션이 루프를 이어받는 법

1. `TODO.md`에서 **다음 지역**을 확인한다
2. `docs/loop-engineering.md`(이 문서) §2로 GOAL·경계를 확인한다
3. 앞선 지역들의 산출물과 **전역 배분표**를 읽는다
4. 그 지역 한 바퀴를 돌린다 → 보고 → 커밋
5. 예산·바퀴 상한에 걸리면 **멈추고 다음 시작점을 TODO에 남긴다**

> ⚠ **루프를 다시 설계하지 마라.** GOAL·항목·순서는 이미 정해져 있다. 바꾸려면 오너 승인이 필요하다.
